## Project context

- **Event:** HEnEx hackathon — *Battery Optimization in the Greek Electricity Market*. Source brief: [Hackathon_final.docx.pdf](../Hackathon_final.docx.pdf).
- **Today:** 2026-04-29. Greece's first standalone batteries entered DAM test mode in April 2026, so there is **no mature battery operating history**. The brief calls this out as intentional data scarcity.
- **Market resolution:** hourly until 2025-09-30, **15-minute MTU from 2025-10-01 onward**. Any model that ignores this will silently average over four 15-min slots and lose the intra-hour spread that is the entire point of the trade.
- **Pitch sentence (canonical):** *Weather-conditioned, degradation-aware day-ahead battery spread optimization for the Greek DAM under data scarcity.*

## Core thesis (the one paragraph that matters)

The battery monetizes recurring statistical structure in the Greek DAM: midday RES surplus → low/negative prices, evening residual-load ramp → high prices, regime-dependent nonlinear spike probability. We **forecast a distribution of clearing prices** (P10/P50/P90 or N scenarios), compute the **distribution of charge-discharge spreads**, and feed that into a **degradation-aware stochastic LP**. Trade only when expected spread clears losses + carry + a forecast-uncertainty buffer. See [STRATEGY.md](STRATEGY.md) for the long form.

## Decisions log

Append-only. Each entry: date, decision, why, where it lives. If a decision changes, add a new entry — do not edit history.

- **2026-04-29 — Strategy framing.** Battery as "long price dispersion / short carry." Public pitch language is "robust day-ahead battery spread optimization." Why: keeps the options-theory edge in our heads without exposing it. Where: [STRATEGY.md](STRATEGY.md), [GLOSSARY.md](GLOSSARY.md).
- **2026-04-29 — Forecast architecture is tiered, not monolithic.** Tier 0 ships a quantile baseline; Tier 1 adds soft regimes; Tier 2 adds HEnEx curve features *only if* historical curves are accessible; Tier 3 adds Greek-specific structural features. Why: ship something every step; do not let a Tier-2 rabbit hole block a working submission. Where: [PLAN.md](PLAN.md), [FORECAST.md](FORECAST.md).
- **2026-04-29 — Soft regimes over hard regimes; three regimes (surplus / normal / scarcity).** Why: regime label is itself a forecast; mixture weights interpolate at boundaries instead of jumping; four regimes splits 7 months of 15-min data too thin. Where: [FORECAST.md](FORECAST.md).
- **2026-04-29 — Train on hourly history, predict at 15-min via intra-hour shape.** Why: only ~7 months of 15-min data exists as of 2026-04-29; insufficient for a regime model standalone. Where: [FORECAST.md](FORECAST.md), [DATA.md](DATA.md).
- **2026-04-29 — CVaR stochastic LP is optimizer-layer, not forecast-layer.** Forecast just emits scenarios. Optimizer starts deterministic-with-buffer (λ_buffer · forecast_error_MAD) and graduates to CVaR once scenarios are wired up. Why: separates concerns; lets the backtest run before the stochastic solver is in place. Where: [OPTIMIZER.md](OPTIMIZER.md).
- **2026-04-29 — Theta is decomposed (cycle + calendar + self-discharge + aux + capital + fixed), not a single `degradation_cost` scalar.** Why: a single scalar lets the optimizer hold at 100% SoC for 14 hours waiting for a peak with no penalty; that is unphysical and presents badly. Where: [STRATEGY.md](STRATEGY.md) §"Hold Cost (Theta) Decomposition", [OPTIMIZER.md](OPTIMIZER.md).
- **2026-04-29 — LP not MILP, until proven necessary.** Use net-power formulation + efficiency penalty so simultaneous charge/discharge is uneconomic; promote to MILP with a binary mode variable only if simulation shows the LP relaxes incorrectly. Why: solver simplicity, faster scenario sweeps. Where: [OPTIMIZER.md](OPTIMIZER.md).
- **2026-04-29 — Option B: forecast features are forecast-vintage only; cleared mix is label-only.** No realized values reach the model at inference. Cleared generation mix from ENTSO-E enters only as the label for regime classification, never as a feature. Why: `res_share = res_fcst / load_fcst` is identity arithmetic from inputs the model already has, so a two-stage "predict mix → predict price" pipeline stacks errors for zero information gain. The real motivation for a regime layer is non-linear kinks at curtailment / scarcity thresholds, which are cheaper to capture inside a single-stage model with piecewise features. Where: [FORECAST.md](FORECAST.md), [DATA.md](DATA.md).
- **2026-04-29 — Tier-0 floor is LightGBM-quantile with kink features.** Three independent quantile models at q ∈ {0.1, 0.5, 0.9}, single-stage, no regime layer. Features include explicit `RL_low_kink` and `RL_high_kink` piecewise terms. Soft regime mixture (Tier 1) must beat this on held-out **pinball loss** before shipping — otherwise it is buying complexity, not skill. Why: tree splits handle kinks natively; if a regime layer doesn't add skill over LGBM-quantile, ship Tier 0. Where: [FORECAST.md](FORECAST.md), [PLAN.md](PLAN.md).
- **2026-04-29 — Weather: WeatherNext 2 (live + post-2024 archive) + ERA5 (pre-2024 training backfill).** Open-Meteo demoted to fallback. Six Greek zones with capacity-weighted aggregates per RES type (solar / wind) and a load-weighted temperature aggregate. Why: ensemble-native (gives P10/P50/P90 of weather and feeds scenario propagation at Tier 2+); ERA5 covers training history before the WeatherNext 2 archive starts. ERA5 is reanalysis, not forecast vintage — disclose the small upward bias on pre-2024 backtest skill in the report. Where: [DATA.md](DATA.md), [weather_sources.py](../weather_sources.py).
- **2026-04-29 — Tier-0 weather contract is `ERA5 (history) + Open-Meteo (live)`; WeatherNext 2 is a drop-in upgrade for the live path when EE auth lands.** Both paths emit the same `solar_weighted_*` / `wind_weighted_*` / `load_weighted_temperature_2m` aggregates downstream, so swapping the live source does not require model retraining. Why: do not block the forecast layer on EE approval (minutes to ~1 day). ERA5 needs only a free CDS API token (`~/.cdsapirc`, ~5 min sign-up at `cds.climate.copernicus.eu`). Where: [FORECAST.md](FORECAST.md), [DATA.md](DATA.md), [weather_sources.py](../weather_sources.py).
- **2026-04-29 — FourCastNet (NVlabs) is explicitly out of scope.** Bigger setup lift than the EE auth wait (CUDA box + PyTorch + multi-GB weights + ERA5 IC pipeline) for no demonstrable hackathon-deliverable advantage over WeatherNext 2 / ERA5 / Open-Meteo. Where: [PLAN.md](PLAN.md) anti-goals.
- **2026-04-29 — Zone capacity weights in `GREEK_ZONES` are placeholders.** DAPEEP monthly bulletin verified to contain national-by-technology breakdown only, no regional split (latest publicly listed bulletin is January 2021 anyway). RAAEY GeoPortal (`geo.rae.gr`) has plant-level data but is JS-rendered (Selenium-only). Current `solar_weight` / `wind_weight` / `load_weight` are order-of-magnitude estimates. Why: forecast skill is far more sensitive to regime modeling and vintage discipline than to weather-aggregation weights; not worth a Selenium build pre-submission. Where: [weather_sources.py](../weather_sources.py).
- **2026-04-29 — Cleared fuel mix lives on ENTSO-E, not HEnEx, for the hourly era.** HEnEx `EL-DAM_Results` does carry per-MTU classification breakdown (Lignite / Natural Gas / RES / Imports / Storage / etc.) but reliably only for the 15-min era post-2025-10-01. For the hourly era ENTSO-E "Actual Generation per Production Type" (back to ~2015) is canonical. Use ENTSO-E regardless of era for consistency. Where: [DATA.md](DATA.md).
- **2026-04-29 — DAM commitment is firm at noon CET D-1.** All 96 MTUs locked; physical deviation pays imbalance settlement. Constraint lives entirely in the optimizer; forecast contract is unchanged. Under firm commitment the CVaR penalty in the stochastic optimizer becomes structurally correct (not just nice-to-have). Where: [OPTIMIZER.md](OPTIMIZER.md).
- **2026-04-29 — Evaluation is a Sharpe ladder, not a single number.** Forecast layer reports pinball loss + P10/P90 coverage. Strategy layer reports Sharpe / Sortino / Information Ratio vs naive baseline / capture rate vs perfect foresight / max drawdown / profit per MWh throughput. Split by regime (summer vs winter, hourly vs 15-min era) to avoid hiding bad slices in a single annualized number. Where: [PLAN.md](PLAN.md), [FORECAST.md](FORECAST.md).
- **2026-04-29 — Forecast ships as a frozen pickle + manifest, not as a re-trained model.** `scripts/freeze_model.py` runs once on the training-data box, writes `models/tier0.pkl` / `models/mad_table.parquet` / `models/manifest.json`. `scripts/predict_tomorrow.py` runs anywhere with internet — no training data on disk, no model retraining — and fetches the day's IPTO + Open-Meteo + macro inputs live, validates feature columns against the manifest, and writes the day's P10/P50/P90 + MAD per row. Why: the demo machine should not need 32k rows of HEnEx archive + ERA5 NetCDFs to run the forecast; only a small pickle. Where: [forecast/freeze_model.py](../scripts/freeze_model.py), [forecast/predict_tomorrow.py](../scripts/predict_tomorrow.py), [FORECAST.md](FORECAST.md) §"Shipping the trained model".
- **2026-04-29 — Tier 0 forecast layer is Prophet (decomposition backbone) + LightGBM-quantile (residual corrector).** Prophet sees timestamp + exogenous regressors (load_fcst, res_fcst, RL, RES_share, gas, carbon) + Greek bank holidays + Orthodox Easter window — *not* lagged price. LightGBM-quantile predicts conditional quantiles of the residual at q ∈ {0.1, 0.5, 0.9} using kink + weather + macro features. Final P_q = prophet_yhat + lgbm_q(residual). Why: Prophet owns calendar effects (which it does well on noisy thin series), LGBM owns non-linear residuals; non-overlapping work. PLAN.md anti-goal still bans *autoregressive* Prophet; the regressor-driven configuration is explicitly allowed. Where: [forecast/](../forecast/), [FORECAST.md](FORECAST.md), [PLAN.md](PLAN.md), [scripts/fit_forecast.py](../scripts/fit_forecast.py), [scripts/predict_day.py](../scripts/predict_day.py).

## Constraints to remember

- **Look-ahead leakage is the failure mode.** Every feature must be available before DAM gate closure (D-1 ≈ 12:00 EET). Realized values → labels and evaluation only. If the backtest looks too good, this is the first place to check.
- **No mocking the database / market.** Backtest uses realized DAM prices and *forecast vintages* of inputs (load forecast, RES forecast, weather forecast). Do not feed realized RL into a model that will be served forecast RL at inference.
- **Don't average over the hourly→15-min transition.** Two regimes of resolution. The model needs to know which one each row is in (`mtu_resolution` column), or you need to subset.
- **Battery telemetry does not exist for Greek standalone assets pre-April-2026.** All battery-side parameters (`eta_ch`, `eta_dis`, `E_max`, `P_ch_max`, `P_dis_max`, `delta_self`, `kappa_cycle`, calendar fade rates, `SoC_threshold`) come from datasheet defaults or industry priors, not from data. Document chosen values in [OPTIMIZER.md](OPTIMIZER.md).
